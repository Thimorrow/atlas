## What this does

**Schema.** `manual_events` bekommt `color` (Hex/Token-String, nullable), `location`
(nullable), `all_day` (boolean, default false). `start_time`/`end_time` werden nullable,
weil Ganztag keine Uhrzeit hat. `routines` bekommt `location` + `all_day` (color schon da).

**Migration.** `drizzle-kit generate` erzeugt `0001_*.sql`. Additive Spalten + Nullable-
Lockerung -> kein Datenverlust. Auf der Neon-DB anwenden (`drizzle-kit migrate` oder
`run_sql`), aber das ist Deploy-Detail; fuer die Verifikation reicht generate + typecheck.

**Validierung (calendar-store).** `parseNewManualEvent`: `color` optional (nonEmptyStr |
null), `location` optional (string | null), `allDay` optional (boolean). Wenn
`allDay !== true`, bleiben `startTime`/`endTime` Pflicht (HH:MM); wenn `allDay === true`,
werden Start/Ende ignoriert/auf null gesetzt. Patch-Parser analog. `parseNewRoutine` /
`parseRoutinePatch`: `location` + `allDay` analog ergaenzen (fixed-Routinen koennen auch
ganztaegig sein, z.B. "Fastentag").

**Expansion.** `CalendarEvent` Typ erhaelt `location?: string | null` und `allDay?: boolean`.
`manualToEvent` setzt `color: e.color` (vorher hart `null`), `location: e.location`,
`allDay: e.allDay`. `routineToEvent` reicht `location` + `allDay` durch. Damit hat das
Frontend in T04 alle Felder zum Rendern (Farbe pro Block, Ort als Unterinfo, Ganztag als
dezenter Balken statt Zeitblock).

Failure cases: ungueltige Farbe/Zeit -> 400 mit Fehlertext (bestehendes Parsed-Muster);
`allDay:true` zusammen mit Start/Ende -> Start/Ende werden verworfen, kein Fehler.
